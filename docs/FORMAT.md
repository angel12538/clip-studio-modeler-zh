# CELSYS 资源文件格式

本文记录 CLIP STUDIO MODELER 的资源文件结构，供后续维护参考。
该格式在 CELSYS 多个产品中通用。

---

## 概览

`resource\<语言>\` 下的每个文件是一个资源包，文件名是 GUID，
没有扩展名。例如：

```
resource\english\403D7B1C-66B6-472d-8440-EA369B3CC9AB
```

每个文件内含若干字符串，是一棵**递归分段树**。

---

## 结构

### 通用节点

```
+0   u32  子段数 N
+4   N × 12 字节的段表
```

每个段表项：

```
+0   u32  id
+4   u32  子段偏移（文件绝对偏移）
+8   u32  子段长度
```

### 叶子

叶子是叶子节点，内容为一个字符串：

```
+0   u32  文本字节数 L
+4   L 字节  UTF-8 文本
```

### 约束

**同层子段必须首尾相接、无空隙，且精确覆盖父段的范围。**

即对相邻两项 `a` 和 `b`：

```
a.offset + a.length == b.offset
```

且第一项的 offset 应等于父节点头部之后的位置，
最后一项的 offset + length 应等于父段结束。

---

## 实例

以 `3D51C869-1035-4A35-BF52-CBA0874A3365`（562 字节）为例：

```
0000  00 00 00 03  子段数 = 3
0004  00 00 00 01  id = 1
0008  00 00 00 28  偏移 = 0x28
000c  00 00 01 a0  长度 = 0x1a0
0010  00 00 00 02  id = 2
0014  00 00 01 c8  偏移 = 0x1c8
0018  00 00 00 52  长度 = 0x52
001c  00 00 00 03  id = 3
0020  00 00 02 1a  偏移 = 0x21a
0024  00 00 00 18  长度 = 0x18
```

验证：`0x28 + 0x1a0 = 0x1c8` ✓，`0x1c8 + 0x52 = 0x21a` ✓

第一个子段 `@0x28` 继续展开：

```
0028  00 00 00 09  子段数 = 9
002c  ...
```

最终每个叶子是一条字符串。

---

## 长度可变

同一 GUID 文件在不同语言版里大小不同：

| 语言 | 文件大小 |
|---|---|
| 日语 | 602 字节 |
| 韩语 | 560 字节 |
| 繁中 | 536 字节 |
| 英语 | 536 字节 |

说明字符串长度不受限制，只要重建时同步更新所有偏移即可。

---

## 重建算法

改字符串长度时，必须**自底向上重建**：

```
1. 递归解析出完整树结构
2. 为每个叶子生成新内容 [u32 新长度][UTF-8 新文本]
3. 从根开始依次输出：
   a. 先为节点头部占位
   b. 递归输出所有子节点，记录它们的实际位置和大小
   c. 回填头部：子段数 + 每项 {id, 偏移, 长度}
4. 校验：重新解析生成结果，结构应与预期一致
```

参考实现 [`tools/celsys_tree.py`](../tools/celsys_tree.py)。

## 陷阱

### 叶子判定不能只看长度前缀

节点头部也以 u32 开头，容易被误判为字符串长度。
判定叶子需同时满足：

```python
L = u32(data, start)
start + 4 + L == start + length      # 长度必须刚好填满
且 L 字节是合法 UTF-8
且无控制字符
```

### 部分文件含二进制叶子

不是所有叶子都是文本。有些叶子是二进制数据（如着色器代码、配置），
重建时原样保留，不参与翻译。

### 顺序不一定与 id 一致

段表里的 `id` 不保证按升序排列，也不保证与物理顺序对应。
应以偏移排序为准，id 仅作标识。

---

## 验证方法

改动后务必做往返测试：

```python
# 不修改任何内容重建，应与原文件逐字节相同
rebuilt = build(original, root, {})
assert rebuilt == original
```

本项目实测 32/32 文件精确往返通过。若某个文件失败，
说明解析或重建逻辑对该结构处理有误，不要强行写入。
